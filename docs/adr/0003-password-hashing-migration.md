# ADR-0003: переход с открытых паролей на BCrypt

- Статус: принято
- Дата: 2026-11-02
- Связанный issue: [#65](https://github.com/AlexeyOs/GoodCourses/issues/65)
- Связанный SDD: [безопасное развёртывание GoodCourses](../specifications/issue-65-production-deployment.md)

## Контекст

Текущая конфигурация использует `NoOpPasswordEncoder`, поэтому локальные пароли могут храниться в базе в открытом виде. Перед размещением приложения в интернете необходимо перейти на адаптивное хеширование и исключить дальнейшее сохранение или сравнение открытого текста.

## Рассмотренные варианты

### Принудительный сброс всех существующих паролей

Локальный вход блокируется до установки нового пароля через проверенный одноразовый сценарий восстановления. Вариант создаёт неудобство пользователям, но позволяет открыть стенд без legacy-паролей и legacy-кода.

### Прозрачное обновление после успешного входа

Система сравнивает введённый пароль со старым открытым значением и после успешного входа сохраняет BCrypt-хеш. Вариант отклонён: публичный production продолжал бы обрабатывать открытые пароли, а неактивные записи оставались бы незащищёнными неопределённое время.

### Массово BCrypt-хешировать содержимое текущего столбца

Технически позволяет входить со старым паролем, но обрабатывает открытые пароли в миграции и оставляет их копии в backup. Вариант отклонён.

## Решение

Использовать принудительный сброс до публичного запуска:

1. Все новые, изменённые и восстановленные пароли кодируются BCrypt.
2. Ввести `password_state`: `ACTIVE`, `RESET_REQUIRED`, `EXTERNAL_ONLY`. Для `ACTIVE` обязателен BCrypt-хеш; для остальных состояний `password IS NULL`.
3. До публикации перевести legacy-записи в `RESET_REQUIRED` и очистить открытое значение после защищённого backup.
4. Уведомить пользователей и потребовать установить новый пароль через проверенный одноразовый сценарий восстановления.
5. Не открывать публичный доступ, пока `plaintext_credential_count` не станет равен нулю и не проверен recovery-канал для `RESET_REQUIRED`.
6. Production-код проверяет только BCrypt и не содержит fallback-сравнения с открытым значением.
7. OAuth-учётные записи без локального пароля обрабатываются отдельно и не получают фиктивный пароль.

Дополнительные требования:

- пароль, BCrypt-хеш и recovery token не выводятся в логах;
- все сервисы установки пароля используют единый `PasswordEncoder`;
- начальный BCrypt cost 12 подтверждается benchmark на production runtime с целью 150–500 мс на проверку;
- пароль длиннее 72 байт в UTF-8 отклоняется; проверяются граничные Unicode-случаи;
- тесты подтверждают, что BCrypt-хеш не понижается до legacy-формата;
- backup с открытыми паролями шифруется, имеет ограниченный доступ и короткий срок хранения;
- после перехода создаётся новый backup, выполняется пробное восстановление, а старые копии уничтожаются по утверждённой политике;
- откат не возвращает образ с `NoOpPasswordEncoder` или базу с активными открытыми паролями.

## Последствия

Положительные:

- production никогда не сравнивает пароль с открытым значением;
- перед публикацией достигается проверяемое состояние без legacy-паролей;
- новые и восстановленные пароли защищены BCrypt.

Отрицательные:

- все существующие пользователи должны восстановить пароль;
- до завершения сброса публичный запуск заблокирован;
- требуется работоспособный и проверенный канал восстановления;
- старые backup требуют защищённой процедуры уничтожения.

## Условия пересмотра

Решение пересматривается только отдельным заменяющим ADR, если подтверждено, что существующих локальных паролей нет или учётные записи можно безопасно удалить и создать заново. Ослабление до прозрачного сравнения с открытым значением не допускается без отдельного принятия риска владельцем проекта.

После завершения миграции ADR остаётся историческим документом. В приложении не должно быть legacy-проверки.

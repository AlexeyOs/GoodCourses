# ADR-0002: версионирование схемы PostgreSQL через Flyway

- Статус: принято
- Дата: 2026-11-02
- Связанный issue: [#65](https://github.com/AlexeyOs/GoodCourses/issues/65)
- Связанный SDD: [безопасное развёртывание GoodCourses](../specifications/issue-65-production-deployment.md)

## Контекст

Сейчас начальная схема находится в `sql/goodcourses-db.sql`, а изменения функций оформлены отдельными SQL-файлами. Приложение не отслеживает, какие изменения уже применены. Ручной запуск SQL создаёт риск пропустить миграцию, применить её дважды или развернуть код с несовместимой схемой.

## Рассмотренные варианты

### Оставить ручные SQL-скрипты

Минимум изменений, но нет истории выполнения, проверки порядка и автоматизации развёртывания.

### Hibernate schema update

Удобен для локальной разработки, но не даёт контролируемой истории, проверки данных и предсказуемого production-отката.

### Liquibase

Поддерживает SQL/XML/YAML/JSON и сложные changeset. Для текущего проекта добавляет больше вариантов и конфигурации, чем требуется.

### Flyway

Использует последовательные SQL-миграции, близок к существующему формату проекта и хранит историю выполнения в самой БД.

## Решение

Использовать Flyway и версионируемые SQL-миграции.

Правила:

- применённые миграции не редактируются;
- каждое изменение схемы получает новую версию;
- Hibernate проверяет соответствие модели, но не изменяет production-схему;
- `V1` является полной текущей схемой из актуального `goodcourses-db.sql` и уже содержит изменения issue #54 и #31;
- для пустой БД применяется `V1`, а изменения #54/#31 не повторяются отдельными версиями;
- существующая БД помечается `baselineVersion=1` только после проверки обязательных объектов и ограничений; расхождение останавливает запуск;
- изменения issue #65 начинаются с `V2`;
- миграции запускаются до создания JPA `EntityManagerFactory`;
- удаление или неоднозначное преобразование пользовательских данных не выполняется автоматически без отдельного решения;
- перед необратимыми изменениями создаётся backup.

## Последствия

Положительные:

- схема воспроизводится из репозитория;
- приложение знает текущую версию БД;
- порядок изменений становится одинаковым локально и в production;
- повторный запуск не применяет выполненные миграции повторно.

Отрицательные:

- требуется аккуратно подготовить baseline;
- ошибочную применённую миграцию нельзя просто исправить редактированием файла;
- откат обычно оформляется новой миграцией или восстановлением backup;
- запуск приложения зависит от успешного завершения миграций.

## Условия пересмотра

Решение пересматривается, если проекту потребуются сложные многодиалектные changeset, встроенный декларативный rollback или централизованное управление схемами нескольких приложений. В таком случае оценивается переход на Liquibase либо отдельный migration job.

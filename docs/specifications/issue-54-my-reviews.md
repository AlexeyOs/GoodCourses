# SDD: вкладка «Мои отзывы»

- Issue: [#54 — Add tab my Reviews](https://github.com/AlexeyOs/GoodCourses/issues/54)
- Статус: готово к реализации
- Тип документа: Software Design Description
- Целевая версия: ближайший функциональный релиз GoodCourses

## 1. Цель

Добавить авторизованному пользователю раздел «Мои отзывы», в котором он может:

- просматривать оставленные им отзывы на курсы;
- переходить со своего отзыва на страницу соответствующего курса;
- редактировать текст собственного отзыва;
- удалять собственный отзыв.

Функция должна исключать чтение через этот раздел, изменение и удаление отзывов другого пользователя путём подстановки идентификатора.

## 2. Текущее состояние

В проекте уже существуют:

- JPA-сущность `FeedBack`;
- таблица `feedback`;
- связь отзыва с `Profile` и `Course`;
- создание отзыва через `POST /add/feedback`;
- вывод отзывов на странице курса;
- скрытие формы создания, если текущий пользователь уже оставил отзыв на этом курсе.

Текущие ограничения реализации:

- отсутствует отдельный список отзывов пользователя;
- отсутствуют операции редактирования и удаления;
- методы `FeedBackRepository.findByProfile(...)` и `findByCourse(...)` возвращают одну запись, хотя связь допускает несколько отзывов;
- правило «один пользователь — один отзыв на курс» не закреплено ограничением базы данных;
- принадлежность отзыва пользователю нельзя безопасно проверить одной репозиторной операцией;
- текст отзыва не проходит полноценную серверную валидацию;
- поле `rating` существует в SQL-схеме, но отсутствует в Java-модели и интерфейсе.

## 3. Границы задачи

### 3.1. Входит в задачу

- пункт меню «Мои отзывы» для авторизованного пользователя;
- страница со списком собственных отзывов;
- пагинация списка;
- отображение информации о курсе, текста отзыва и дат;
- переход на страницу курса;
- редактирование текста отзыва;
- удаление отзыва после подтверждения;
- серверная проверка владельца;
- серверная валидация текста;
- ограничение одного отзыва пользователя на один курс;
- согласование JPA-модели и SQL-схемы в затронутой области;
- автоматические и ручные проверки пользовательских сценариев.

### 3.2. Не входит в задачу

- оценки курсов и поле `rating`;
- модерация отзывов;
- ответы на отзывы;
- реакции и жалобы;
- публичная страница всех отзывов конкретного пользователя;
- изменение структуры страницы курса, не связанное с отзывами;
- переименование класса `FeedBack` в `Feedback`;
- переход на REST API или SPA;
- soft delete и история версий отзывов.

Поле `rating` намеренно исключено: issue #54 описывает вкладку отзывов, а добавление рейтинга является отдельной пользовательской функцией и требует самостоятельных правил отображения и агрегации.

## 4. Пользовательские сценарии

### 4.1. Просмотр списка

1. Авторизованный пользователь открывает меню.
2. Выбирает «Мои отзывы».
3. Система отображает только отзывы текущего пользователя от новых к старым.
4. Для каждого отзыва доступны курс, текст, даты и разрешённые действия.

### 4.2. Пустой список

1. Пользователь открывает раздел, не имея отзывов.
2. Система показывает сообщение «Вы ещё не оставляли отзывы».
3. Пользователю доступна ссылка «Перейти к списку курсов».

### 4.3. Редактирование

1. Пользователь нажимает «Редактировать» у собственного отзыва.
2. Система открывает форму с текущим текстом.
3. Пользователь изменяет текст и сохраняет форму.
4. Система проверяет владельца и валидирует текст.
5. Система сохраняет изменение, обновляет `lastUpdate` и возвращает пользователя в список.

### 4.4. Удаление

1. Пользователь нажимает «Удалить».
2. Интерфейс запрашивает подтверждение.
3. После подтверждения система повторно проверяет владельца и удаляет отзыв.
4. Отзыв исчезает из раздела «Мои отзывы» и со страницы курса.

### 4.5. Попытка доступа к чужому отзыву

1. Пользователь подставляет идентификатор чужого отзыва в URL или форму.
2. Репозиторий не возвращает запись для комбинации `feedbackId + currentProfileId`.
3. Система не изменяет данные и возвращает HTTP 404.

Для такого случая выбран 404, а не 403, чтобы не подтверждать существование чужого отзыва.

## 5. Маршруты

| Метод | Маршрут | Назначение | Доступ |
|---|---|---|---|
| `GET` | `/my-reviews` | Список отзывов текущего пользователя | `USER` |
| `GET` | `/my-reviews/{id}/edit` | Форма редактирования | владелец |
| `POST` | `/my-reviews/{id}/edit` | Сохранение изменений | владелец |
| `POST` | `/my-reviews/{id}/delete` | Удаление | владелец |
| `POST` | `/add/feedback` | Создание отзыва на странице курса | `USER` |

После успешного `POST` используется redirect:

- редактирование и удаление: `redirect:/my-reviews`;
- создание: `redirect:/course/{courseId}`.

Все маршруты `/my-reviews/**` и `/add/feedback` должны быть явно защищены в `SecurityConfig` ролью `USER`.

## 6. Представление данных формы

Не следует привязывать HTTP-форму напрямую к JPA-сущности. Требуется отдельный DTO:

```java
public class FeedbackForm {
    @NotBlank
    @Size(max = 2000)
    private String description;
}
```

Если используемая версия Bean Validation не предоставляет `javax.validation.constraints.NotBlank`, применяется `org.hibernate.validator.constraints.NotBlank`.

Форма не должна передавать:

- `profileId`;
- владельца отзыва;
- дату создания;
- дату изменения;
- объект курса.

Идентификатор текущего профиля берётся только из `SecurityUtil`/контекста Spring Security.

Перед сохранением текст обрезается через `trim()`. Строка, ставшая пустой после обрезки, считается невалидной.

## 7. Изменения слоёв приложения

### 7.1. Repository

`FeedBackRepository` должен предоставлять операции, ограниченные профилем:

```java
@EntityGraph(attributePaths = "course")
Page<FeedBack> findAllByProfileIdOrderByStartDateDesc(
        long profileId,
        Pageable pageable);

Optional<FeedBack> findByIdAndProfileId(
        long feedbackId,
        long profileId);

boolean existsByCourseIdAndProfileId(
        long courseId,
        long profileId);
```

Существующие одиночные методы:

```java
FeedBack findByProfile(Profile profile);
FeedBack findByCourse(Course course);
```

следует удалить либо заменить методами с корректной множественностью после проверки всех мест использования.

`@EntityGraph(attributePaths = "course")` необходим для списка, чтобы JSP не инициировал отдельный запрос курса для каждого отзыва и не зависел от открытой Hibernate-сессии.

### 7.2. Service

Вместо сервиса, отвечающего только за добавление, вводится единый контракт:

```java
public interface FeedbackService {
    Page<FeedBack> findMyReviews(long profileId, Pageable pageable);

    FeedBack create(
            long profileId,
            long courseId,
            FeedbackForm form);

    FeedBack findOwned(
            long profileId,
            long feedbackId);

    FeedBack update(
            long profileId,
            long feedbackId,
            FeedbackForm form);

    void delete(
            long profileId,
            long feedbackId);
}
```

Требования к реализации:

- `create`, `update` и `delete` выполняются в транзакции;
- профиль и курс загружаются внутри сервиса;
- перед созданием проверяется отсутствие отзыва на эту пару профиль/курс;
- `update` и `delete` загружают отзыв через `findByIdAndProfileId`;
- `startDate` устанавливается только при создании;
- `lastUpdate` устанавливается при каждом успешном изменении;
- контроллер не обращается к репозиториям напрямую.

### 7.3. Controller

Рекомендуется создать `MyReviewsController` для списка и управления отзывами пользователя.

Существующий `FeedbackController` должен использовать `FeedbackService` для создания отзыва. Прямые обращения к `CourseRepository` и `ProfileRepository` из него удаляются.

Ошибки:

- несуществующий курс: HTTP 404;
- несуществующий или чужой отзыв: HTTP 404;
- повторный отзыв на курс: контролируемая ошибка формы либо редирект на курс с сообщением;
- ошибка валидации: повторный показ формы с введённым текстом.

## 8. Интерфейс

### 8.1. Меню

В меню авторизованного пользователя добавляется ссылка:

```text
Мои отзывы
```

Ссылка ведёт на `${pageContext.request.contextPath}/my-reviews`.

### 8.2. Список отзывов

Новая JSP-страница:

```text
src/main/webapp/WEB-INF/JSP/my-reviews.jsp
```

Карточка или строка отзыва содержит:

- тему изучения курса;
- платформу;
- автора курса;
- текст отзыва с безопасным экранированием;
- дату создания;
- дату изменения, если она задана;
- ссылку «Перейти к курсу»;
- кнопку «Редактировать»;
- кнопку «Удалить».

Удаление должно работать обычной POST-формой. JavaScript может показывать подтверждение, но не должен быть единственным способом выполнить операцию.

### 8.3. Пагинация

Список использует `Pageable` и параметр `page`, начиная с нуля. Размер страницы фиксируется сервером, рекомендуемое значение — 10 отзывов.

Интерфейс показывает:

- «Предыдущая», если существует предыдущая страница;
- «Следующая», если существует следующая страница;
- текущий номер страницы в пользовательском формате, начиная с единицы.

## 9. Модель и база данных

### 9.1. Согласование nullable

JPA-модель и SQL должны одинаково считать обязательными:

- `description`;
- `start_date`.

Для новой установки схема должна содержать:

```sql
ALTER TABLE feedback
    ALTER COLUMN description SET NOT NULL,
    ALTER COLUMN start_date SET NOT NULL;
```

Перед применением к существующей базе необходимо проверить наличие `NULL`. Автоматически удалять или заменять такие данные нельзя без отдельного решения владельца проекта.

### 9.2. Уникальность отзыва

На уровне базы вводится ограничение:

```sql
ALTER TABLE feedback
    ADD CONSTRAINT uq_feedback_course_profile
    UNIQUE (course_id, profile_id);
```

Перед добавлением ограничения в существующую базу необходимо найти дубликаты:

```sql
SELECT course_id, profile_id, COUNT(*)
FROM feedback
GROUP BY course_id, profile_id
HAVING COUNT(*) > 1;
```

Если дубликаты обнаружены, миграция останавливается. Решение о сохранении конкретной записи принимается отдельно.

### 9.3. Внешние ключи

Необходимо проверить наличие внешних ключей:

- `feedback.course_id -> course.id`;
- `feedback.profile_id -> profile.id`.

Удаление курса или профиля не должно неявно каскадно удалять отзывы без отдельного согласованного решения.

## 10. Безопасность

- UI скрывает раздел от гостя, но основная защита выполняется Spring Security.
- Владелец определяется только по текущей аутентифицированной сессии.
- `profileId` не принимается из формы или URL.
- Изменение и удаление используют запрос по `feedbackId + profileId`.
- Пользовательский текст выводится через `<c:out>` либо эквивалентное экранирование.
- Содержимое отзыва не интерпретируется как HTML.
- Удаление выполняется POST-запросом.
- В рамках задачи нельзя дополнительно ослаблять CSRF-защиту.

В проекте CSRF глобально отключён существующей конфигурацией. Его включение является отдельной задачей безопасности; текущая функция не должна расширять область этого решения.

## 11. Конкурентность и целостность

Проверка `existsByCourseIdAndProfileId` улучшает пользовательское сообщение, но не обеспечивает уникальность при одновременных запросах. Окончательная гарантия обеспечивается ограничением `uq_feedback_course_profile`.

Нарушение уникальности должно преобразовываться в контролируемую ошибку, а не возвращать пользователю stack trace.

Для редактирования оптимистическая блокировка в рамках issue #54 не вводится. Последнее успешное сохранение побеждает. При необходимости защита от потерянного обновления должна оформляться отдельной задачей с полем `@Version`.

## 12. Критерии приёмки

1. Гость при открытии `/my-reviews` перенаправляется на страницу входа.
2. Авторизованный пользователь видит пункт «Мои отзывы».
3. Список содержит только отзывы текущего пользователя.
4. Список отсортирован по `startDate` от новых к старым.
5. Пустой список содержит объяснение и ссылку на каталог курсов.
6. Из каждого отзыва можно перейти на соответствующий курс.
7. Валидный текст собственного отзыва успешно изменяется.
8. После изменения устанавливается `lastUpdate`.
9. Пустой текст и текст длиннее 2000 символов не сохраняются.
10. Ошибка валидации возвращает форму с ранее введённым значением.
11. Собственный отзыв успешно удаляется после подтверждения.
12. Удалённый отзыв исчезает из списка и со страницы курса.
13. Чужой отзыв нельзя открыть для редактирования, изменить или удалить подстановкой ID.
14. Второй отзыв пользователя на тот же курс не создаётся.
15. Ограничение уникальности действует при конкурентных запросах.
16. Пагинация не смешивает отзывы разных пользователей.
17. Пользовательский текст отображается как текст и не исполняет HTML/JavaScript.

## 13. План тестирования

### 13.1. Repository

- выборка страницы только по заданному `profileId`;
- сортировка от новых к старым;
- поиск существующего собственного отзыва;
- отсутствие результата для чужого `profileId`;
- проверка существования по паре курс/профиль.

### 13.2. Service

- создание валидного отзыва;
- отказ при повторном отзыве;
- установка `startDate`;
- редактирование собственного отзыва;
- установка `lastUpdate`;
- отказ при редактировании чужого отзыва;
- удаление собственного отзыва;
- отказ при удалении чужого отзыва;
- отказ для несуществующего курса и отзыва.

### 13.3. Controller и Security

- редирект гостя на вход;
- успешный список для пользователя с ролью `USER`;
- корректная модель списка и пагинации;
- повторный показ формы при ошибке валидации;
- redirect после успешного POST;
- HTTP 404 для чужого или несуществующего отзыва.

### 13.4. Сквозная проверка

1. Авторизоваться пользователем A.
2. Создать отзыв на курс.
3. Убедиться, что отзыв виден на курсе и в «Моих отзывах».
4. Изменить текст и проверить обе страницы.
5. Авторизоваться пользователем B и попытаться использовать ID отзыва A.
6. Убедиться, что чтение формы, изменение и удаление запрещены.
7. Вернуться пользователем A, удалить отзыв и проверить обе страницы.
8. Проверить серверные логи на отсутствие необработанных исключений.

## 14. Последовательность реализации

1. Проверить фактические ограничения и данные существующей БД.
2. Обновить SQL-схему и добавить уникальное ограничение.
3. Добавить `FeedbackForm`.
4. Исправить `FeedBackRepository`.
5. Создать `FeedbackService` и реализацию.
6. Перевести существующее создание отзыва на новый сервис.
7. Добавить `MyReviewsController`.
8. Защитить маршруты в `SecurityConfig`.
9. Добавить JSP списка и формы редактирования.
10. Добавить пункт меню.
11. Реализовать тесты.
12. Выполнить сборку, интеграционную и ручную проверку.

## 15. Риски

| Риск | Мера снижения |
|---|---|
| В существующей базе есть дубликаты отзывов | диагностический SQL до уникального ограничения |
| В существующей базе есть `NULL` в обязательных полях | предварительная проверка и остановка миграции |
| N+1 при выводе курса | `@EntityGraph(attributePaths = "course")` |
| Изменение чужого отзыва | запрос по `id + profileId` в сервисном сценарии |
| Повторный отзыв при гонке | уникальное ограничение PostgreSQL |
| XSS через текст отзыва | экранированный вывод через JSTL |
| Регрессия существующей формы курса | перевести создание на общий сервис и покрыть тестом |
| Поломанные старые интеграционные тесты окружения | выполнить доступные проверки и отдельно зафиксировать исходную проблему |

## 16. Условия готовности

Задача считается завершённой, когда:

- выполнены все критерии приёмки;
- SQL и JPA согласованы;
- сборка `mvn package -DskipTests` успешна;
- применимые автоматические тесты пройдены;
- вручную проверены владелец, другой пользователь и гость;
- в diff отсутствуют секреты, локальные настройки, `.runtime/`, `.tools/` и `target/`;
- pull request содержит описание проверки и известных ограничений.

# SDD: безопасное развёртывание GoodCourses в интернете

- Issue: [#65 — Подготовить безопасное развёртывание GoodCourses в интернете](https://github.com/AlexeyOs/GoodCourses/issues/65)
- Статус: проект решения
- Тип документа: Software Design Description
- Целевая версия: первый публичный стенд GoodCourses
- Связанные ADR:
  - [ADR-0001: платформонезависимый контейнер и Neon PostgreSQL](../adr/0001-production-hosting-and-database.md)
  - [ADR-0002: версионирование схемы через Flyway](../adr/0002-database-schema-migrations.md)
  - [ADR-0003: переход с открытых паролей на BCrypt](../adr/0003-password-hashing-migration.md)

## 1. Цель

Подготовить GoodCourses к безопасному и воспроизводимому размещению в интернете для небольшой группы пользователей с минимальной стоимостью эксплуатации.

Результатом должен стать публичный HTTPS-стенд, который:

- запускается из одного Docker-образа;
- хранит постоянные данные в Neon PostgreSQL;
- обновляет схему версионируемыми миграциями;
- не хранит пароли и инфраструктурные секреты в открытом виде;
- переживает перезапуск и повторное развёртывание без потери данных;
- имеет документированные процедуры запуска, проверки, резервного копирования и отката.

## 2. Текущее состояние

В проекте уже существуют WAR-сборка, Tomcat 9, Dockerfile, Docker Compose, `Procfile`, SQL-схема и отдельные SQL-файлы изменений.

Перед публичным запуском необходимо устранить следующие ограничения:

- `NoOpPasswordEncoder` сохраняет пароли без безопасного хеширования;
- CSRF-защита отключена глобально;
- ключ remember-me задан в коде;
- production-профиль содержит `app.host=http://localhost:8080`;
- конфигурации зависят от локальных путей и обязательных SMTP/OAuth placeholders;
- схема БД обновляется вручную, Flyway/Liquibase отсутствует;
- Dockerfile ожидает заранее собранный WAR и использует плавающий образ `tomcat:9`;
- нет отдельной проверки состояния приложения и описанного процесса отката;
- Maven-сборка изменяет `src/main/resources/application.properties`, что ухудшает воспроизводимость.

## 3. Границы задачи

### 3.1. Входит в задачу

- безопасное хеширование паролей и принудительный сброс существующих локальных паролей до публикации;
- включение CSRF для изменяющих запросов;
- перенос production-настроек и секретов в окружение;
- автоматическое управление схемой PostgreSQL;
- переносимый production Docker-образ;
- подключение Neon PostgreSQL по SSL;
- health-check, структурированные логи и базовая диагностика запуска;
- пробное развёртывание на совместимом Docker-хостинге;
- документация эксплуатации, backup и rollback;
- автоматические и ручные проверки ключевых пользовательских сценариев.

### 3.2. Не входит в задачу

- переход приложения на Spring Boot;
- Kubernetes, высокая доступность и горизонтальное масштабирование;
- изменение пользовательских функций курсов, профилей и отзывов;
- перенос внешних изображений в объектное хранилище, пока не появится загрузка пользовательских файлов;
- обязательный выбор платного тарифа или конкретного провайдера до пробного развёртывания;
- массовая модернизация всех зависимостей, не требуемая для безопасного запуска.

## 4. Целевая архитектура

```text
Пользователь
    |
    | HTTPS
    v
Docker-хостинг
    |
    | Tomcat 9 + GoodCourses.war
    |
    | JDBC over TLS
    v
Neon PostgreSQL
```

Контейнер приложения является stateless: конфигурация поступает из окружения, а постоянные бизнес-данные находятся в PostgreSQL. Выбор между Render, Koyeb и другим Docker-хостингом выполняется после проверки обязательных требований из раздела 13.

## 5. Конфигурация окружения

Production-профиль не должен содержать реальные секреты и локальные пути. Минимальный контракт окружения:

| Переменная | Обязательность | Назначение |
|---|---:|---|
| `DATABASE_URL` | да | строка подключения Neon PostgreSQL с SSL |
| `APP_HOST` | да | внешний HTTPS URL без завершающего `/` |
| `REMEMBER_ME_KEY` | да | случайный ключ remember-me |
| `PORT` | зависит от платформы | HTTP-порт контейнера |
| `SMTP_ENABLED` | нет; обязательно при наличии legacy-пользователей | включает отправку писем и восстановление пароля |
| `SMTP_HOST`, `SMTP_PORT` | при включённой почте | SMTP-сервер |
| `SMTP_USERNAME`, `SMTP_PASSWORD` | при включённой почте | SMTP-учётные данные |
| `FACEBOOK_CLIENT_ID`, `FACEBOOK_SECRET` | при включённом OAuth | вход через Facebook |

Если почта или OAuth отключены, соответствующие компоненты не должны препятствовать старту приложения. Исключение: при наличии учётных записей `RESET_REQUIRED` публичный запуск разрешён только с проверенным recovery-каналом — SMTP либо отдельно согласованным одноразовым административным процессом. Значения секретов запрещено выводить в логах.

## 6. Безопасность

### 6.1. Пароли

Новые и изменённые пароли кодируются `BCryptPasswordEncoder`. До открытия публичного доступа все существующие локальные пароли инвалидируются, а пользователи устанавливают новые через проверенный сценарий восстановления. Стратегия описана в ADR-0003.

Все пути установки пароля должны использовать один сервис кодирования:

- регистрация;
- изменение пароля;
- восстановление пароля;
- создание профиля через дополнительные сценарии, если они сохраняют локальный пароль.

Для credentials вводится поле `password_state` со значениями:

- `ACTIVE` — `password` содержит допустимый BCrypt-хеш;
- `RESET_REQUIRED` — локальный вход запрещён, `password IS NULL`, доступно только восстановление;
- `EXTERNAL_ONLY` — профиль использует внешний вход, `password IS NULL`.

Миграция переводит legacy-записи в `RESET_REQUIRED` и очищает открытое значение после создания защищённого backup. Ограничение БД согласует состояние и nullable-поле: хеш обязателен только для `ACTIVE`, а для остальных состояний пароль отсутствует. `plaintext_credential_count` — число непустых значений `password`, не соответствующих BCrypt и состоянию `ACTIVE`; перед публикацией оно обязано быть равно нулю. Production-код не сравнивает введённый пароль с открытым значением.

Если существуют `RESET_REQUIRED`, до публикации обязательно проверяется доставка одноразового recovery token либо утверждённый административный одноразовый процесс. Token хранится только как хеш, имеет короткий срок жизни и одноразовое использование.

Начальный BCrypt cost — 12, но перед реализацией он подтверждается измерением на выбранном runtime с целевой длительностью проверки 150–500 мс. Пароль принимается только если он не превышает 72 байта в UTF-8; дополнительно сохраняется существующий разумный лимит символов. Граничные Unicode-случаи проверяются тестами.

### 6.2. CSRF

Глобальный `csrf().disable()` удаляется. До изменения конфигурации составляется инвентарь всех изменяющих маршрутов, форм и JavaScript-запросов с указанием способа передачи токена и теста. Все POST-формы должны отправлять токен Spring Security. Для обычных JSP-форм используется скрытое поле; AJAX-запросы, если они останутся, передают токен заголовком. Выход выполняется POST-запросом с CSRF-токеном, а не GET-ссылкой.

Отключать CSRF для существующих пользовательских маршрутов нельзя. Исключения допустимы только для отдельно документированных внешних webhook-маршрутов.

### 6.3. HTTPS и cookie

Приложение должно корректно учитывать forwarded-заголовки только от доверенного reverse proxy. Session и remember-me cookie должны использовать `Secure`, `HttpOnly` и подходящий `SameSite`. Внешние callback URL строятся из проверенного `APP_HOST`, а не из недоверенного заголовка запроса. Прямой клиент не должен иметь возможность подменить схему или хост через `Forwarded`/`X-Forwarded-*`.

## 7. База данных и миграции

Flyway запускается до инициализации JPA. Hibernate не должен самостоятельно изменять production-схему.

План формирования истории:

1. `V1` содержит полную текущую схему из актуального `sql/goodcourses-db.sql`, уже включающую изменения issue #54 и #31. Эти изменения отдельными Flyway-миграциями повторно не выполняются.
2. Для пустой БД Flyway применяет `V1`, затем все будущие версии.
3. Для существующей БД перед установкой baseline проверяются обязательные таблицы, ограничения #54/#31 и контрольный набор метаданных. Только совпавшая схема помечается `baselineVersion=1`; при расхождении процесс останавливается.
4. Изменения issue #65 начинаются с `V2` и не редактируют `V1` после первого применения.
5. Проверить обе траектории: новая пустая БД и обновление проверенной копии существующей БД.

Перед destructive или необратимыми изменениями требуется backup. Миграция не должна автоматически удалять неоднозначные пользовательские данные.

Пул соединений настраивается с учётом ограничений бесплатного Neon. Поддерживаемый формат `DATABASE_URL` и его преобразование в JDBC URL документируются и тестируются. Query-параметры исходного URL нельзя терять при разборе. Для Neon требуется проверка сертификата и имени хоста (`sslmode=verify-full` либо эквивалентная настройка драйвера с доверенным CA); простого шифрования без проверки сервера недостаточно. Ошибка формата или TLS приводит к fail-fast без логирования credentials.

## 8. Контейнер и запуск

Production Dockerfile выполняет две стадии:

1. Maven собирает проверенный WAR.
2. Закреплённый образ Tomcat 9 запускает WAR как ROOT-приложение.

Требования к образу:

- повторяемая сборка из чистого клона;
- закреплённые версии базовых образов;
- поддерживаемая patch-версия JDK и Tomcat 9, выбранная после проверки совместимости;
- отсутствие Maven-кэша, исходников, `.runtime/`, `.tools/`, `target/` и локальных секретов в runtime-слое;
- запуск без root, если выбранный базовый образ это поддерживает;
- получение конфигурации только из окружения;
- поддержка модели порта выбранной платформы;
- корректное завершение по `SIGTERM`.

Локальный Docker Compose остаётся средством разработки. `POSTGRES_HOST_AUTH_METHOD=trust` не используется вне локального окружения.

## 9. Health-check и наблюдаемость

Вводятся две read-only проверки без служебных подробностей в ответе:

- liveness подтверждает, что web-процесс не завис, и не обращается к БД;
- readiness выполняет ограниченный по времени запрос к Neon и возвращает успешный статус только когда приложение может обслуживать пользовательские запросы.

Docker-хостинг направляет трафик и оценивает готовность релиза по readiness URL. Недоступность Neon возвращает неуспешный HTTP-статус readiness без утечки строки подключения. Таймаут DB-проверки должен быть меньше таймаута health-check платформы.

Логи выводятся в stdout/stderr, содержат понятную причину отказа запуска и не включают пароли, токены, cookie или полные URL с credentials.

Перед публикацией выполняется проверка зависимостей и container image на известные уязвимости. Critical/High findings устраняются либо для каждого оформляется отдельное, ограниченное по сроку принятие риска владельцем проекта. Массовое обновление зависимостей не требуется, если проверенный patch-релиз и точечные обновления закрывают найденный риск.

## 10. Развёртывание и откат

Перед релизом создаётся зашифрованный backup существующей БД с ограниченным доступом и установленным сроком хранения. После удаления legacy-паролей создаётся новый backup, а старые копии с открытыми паролями удаляются по утверждённой политике. Выпуск выполняется в порядке:

1. собрать и проверить образ;
2. проверить миграции на копии данных;
3. сохранить backup;
4. развернуть новую версию;
5. дождаться успешного health-check;
6. выполнить smoke-тесты.

Откат к предыдущему образу допустим только если применённые миграции обратно совместимы и старый образ не возвращает `NoOpPasswordEncoder`. Для необратно совместимой схемы требуется отдельный план восстановления из совместимого backup. До публикации выполняется пробное восстановление; оно не должно возвращать открытые пароли или требовать legacy-код аутентификации.

## 11. Этапы реализации

1. Безопасность: BCrypt, принудительный сброс legacy-паролей, инвентарь CSRF-маршрутов, remember-me и тесты.
2. Конфигурация: окружение, переносимые notification templates, optional SMTP/OAuth.
3. Flyway: baseline, история миграций и проверки двух траекторий обновления.
4. Контейнер: multi-stage build, health-check и локальный smoke-тест.
5. Пробный деплой: Neon, один или несколько Docker-хостингов, HTTPS и эксплуатационная документация.

Каждый этап выполняется отдельным PR либо небольшой связанной группой PR. Нельзя одновременно включать BCrypt и CSRF без адаптации и проверки всех затронутых сценариев.

## 12. Стратегия проверки

### 12.1. Автоматические проверки

- регистрация сохраняет BCrypt-хеш, а не исходный пароль;
- пользователь с корректным паролем входит, с неверным — нет;
- legacy-пароли инвалидируются до публикации, а восстановленный пароль сохраняется как BCrypt;
- запросы к каждому изменяющему маршруту без CSRF отклоняются, а с токеном проходят;
- logout допускается только через POST с CSRF;
- миграции применяются к пустой и существующей БД;
- повторный запуск миграций ничего не изменяет;
- production-конфигурация не стартует без обязательных секретов и не раскрывает их;
- разбор Neon URL сохраняет TLS-параметры, проверяет сертификат и имя хоста и fail-fast завершает запуск при ошибке;
- session и remember-me cookie имеют ожидаемые `Secure`, `HttpOnly`, `SameSite`;
- недоверенные forwarded-заголовки не меняют внешний URL, redirect или OAuth callback;
- dependency scan и image scan не содержат непринятых Critical/High findings;
- Docker-образ собирается из чистого checkout.

### 12.2. Ручные сценарии

- открыть каталог как гость;
- зарегистрироваться, войти и выйти;
- восстановить legacy-учётную запись и изменить новый пароль;
- изменить профиль и навыки;
- добавить курс в профиль;
- создать, отредактировать и удалить собственный отзыв;
- убедиться, что чужие данные изменить нельзя;
- перезапустить контейнер и проверить сохранность данных;
- выполнить повторное развёртывание и проверить миграции и health-check;
- восстановить зашифрованный backup в тестовую БД и проверить совместимость схемы и входа.

## 13. Выбор Docker-хостинга

Пробное развёртывание оценивает кандидатов по одинаковым критериям:

- запуск обычного Dockerfile без vendor-specific изменений приложения;
- постоянный HTTPS URL;
- безопасное хранение переменных окружения;
- поддержка health-check и логов;
- совместимость с Neon и исходящими TLS-соединениями;
- стоимость при небольшом трафике;
- поведение при простое и время холодного старта;
- возможность быстро откатить образ.

Итоговый провайдер и обнаруженные ограничения фиксируются новым ADR после пробного запуска.

## 14. Критерии приёмки

1. Из чистого клона собирается production Docker-образ без ручного копирования WAR.
2. Приложение доступно по публичному HTTPS URL; liveness и readiness имеют разные URL, а хостинг использует readiness с bounded DB check.
3. Данные находятся в Neon и сохраняются после перезапуска и повторного деплоя.
4. Схема создаётся и обновляется только Flyway-миграциями.
5. Все активные локальные пароли хранятся только как BCrypt-хеши; перед публикацией `plaintext_credential_count = 0`.
6. Legacy-пароли инвалидированы в состояние `RESET_REQUIRED`, recovery-канал проверен, production не содержит legacy-сравнения.
7. CSRF включён, все основные пользовательские формы работают.
8. Секреты отсутствуют в репозитории, образе и логах.
9. README описывает переменные, развёртывание, ограничения тарифа, backup и rollback.
10. Проверены TLS Neon, атрибуты cookie, доверие proxy-заголовкам и все изменяющие CSRF-маршруты.
11. Зафиксированы patch-версии JDK/Tomcat; отсутствуют непринятые Critical/High findings dependency/image scan.
12. Проверены зашифрованный backup, срок хранения, доступ, восстановление и совместимость отката.
13. Выполнены Maven-сборка, применимые тесты и сквозная проверка развёрнутого стенда.

## 15. Риски и открытые вопросы

- Бесплатный хостинг может останавливать приложение при простое и менять условия тарифа.
- В существующей БД могут находиться открытые пароли; публичный запуск блокируется до их полной инвалидации и удаления.
- Включение CSRF затрагивает все изменяющие формы проекта и может выявить неучтённые POST-запросы.
- Baseline должен точно соответствовать реально используемой production-схеме, а не только SQL-файлу в репозитории.
- Старые версии Java, Spring и Tomcat могут потребовать точечных обновлений после обязательного security scan.
- Нужно решить, включать ли SMTP и Facebook OAuth на первом стенде или временно отключить их.

Документ считается готовым к реализации после согласования ADR. Конкретный хостинг может быть выбран позднее, после пробного развёртывания, но security gates обязательны для любого провайдера.

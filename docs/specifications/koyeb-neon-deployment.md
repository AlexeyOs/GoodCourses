## 1. Цель

Развернуть текущий GoodCourses без перехода на Spring Boot как публичный HTTPS-сервис для небольшой группы пользователей, используя только бесплатный Web Service Koyeb и бесплатный проект Neon PostgreSQL.

Решение должно:

- помещаться в 512 МБ RAM и работать на 0,1 vCPU без циклических перезапусков;
- сохранять постоянные данные при scale-to-zero, перезапуске и повторном развёртывании Koyeb;
- исключать автоматическое создание платных ресурсов;
- использовать существующий Docker-образ Tomcat 9 и версионированные миграции Flyway;
- хранить секреты только в Koyeb Secrets;
- позволять перенести контейнер на другой хостинг без изменения бизнес-кода и миграции базы.

## 2. Границы

### 2.1. Входит в реализацию

- подготовка production-конфигурации для запуска в Koyeb;
- ограничение памяти JVM, потоков Tomcat и пула PostgreSQL;
- подключение к Neon по TLS;
- настройка Koyeb Web Service, порта, health-check и secrets;
- проверка миграций, холодного старта, памяти и основных пользовательских сценариев;
- проверка сохранности данных после перезапуска и повторного деплоя;
- инструкция по выпуску, диагностике, backup и откату.

### 2.2. Не входит в реализацию

- миграция на Spring Boot, Java 17/21 или GraalVM;
- использование базы PostgreSQL от Koyeb;
- платные экземпляры, volumes, workers, autoscaling и высокая доступность;
- хранение пользовательских файлов на диске контейнера;
- подключение WAF, отдельного load balancer или Kubernetes;
- изменение функций профилей, курсов и отзывов;
- постоянная работа без холодного старта и формальный SLA.

## 3. Ограничения платформы

Проектирование исходит из условий Koyeb Free на дату документа:

- одна организация может использовать один бесплатный Web Service;
- экземпляр предоставляет 512 МБ RAM, 0,1 vCPU и 2 ГБ временного SSD;
- доступные регионы — Frankfurt и Washington, D.C.;
- постоянный Volume подключить к бесплатному экземпляру нельзя;
- после часа без входящего трафика экземпляр масштабируется до нуля;
- произвольная горизонтальная конфигурация недоступна.

Условия тарифа проверяются повторно непосредственно перед созданием сервиса. Организация должна находиться на Starter, а instance type должен быть ровно `free`. Платная база Koyeb, дополнительный instance, Volume и Pro-план не создаются.

## 4. Целевая архитектура

```text
Пользователь
    |
    | HTTPS
    v
Koyeb Edge / TLS
    |
    | HTTP на PORT внутри контейнера
    v
Koyeb Free Web Service
    |-- Tomcat 9
    |-- GoodCourses.war как ROOT
    |-- временная файловая система
    |
    | JDBC + TLS, sslmode=verify-full
    v
Neon Free PostgreSQL, регион EU
    |-- постоянные бизнес-данные
    |-- Flyway schema history
    `-- backup/restore средствами PostgreSQL и Neon
```

Koyeb завершает публичный TLS. Приложение слушает порт, переданный платформой через `PORT`. Контейнер остаётся stateless. Весь пользовательский контент, который требуется пережить перезапуск, хранится в Neon либо во внешнем хранилище, выбранном отдельным решением.

## 5. Компоненты и ответственность

### 5.1. Koyeb

- собирает image из `docker/tomcat/Dockerfile`;
- запускает один Web Service типа `free` во Frankfurt;
- предоставляет публичный HTTPS URL;
- передаёт конфигурацию и секреты через environment variables;
- перезапускает контейнер при отказе;
- выполняет HTTP health-check по `/health/live`;
- хранит потоковые runtime-логи в пределах возможностей бесплатного тарифа.

### 5.2. Контейнер GoodCourses

- принимает и проверяет `PORT`;
- запускает Tomcat от непривилегированного пользователя;
- применяет Flyway до начала пользовательской работы;
- обслуживает приложение из корневого context path;
- выдаёт раздельные liveness и readiness;
- пишет логи только в stdout/stderr;
- корректно завершается по `SIGTERM`.

### 5.3. Neon

- хранит профили, курсы, навыки, отзывы и служебные данные;
- сохраняет данные независимо от жизненного цикла Koyeb;
- принимает только TLS-подключения с проверкой сертификата и имени хоста;
- ограничивает доступ отдельными production credentials;
- предоставляет точку восстановления и позволяет выполнить логический backup.

## 6. Изменения конфигурации проекта

Текущий профиль Maven `heroku` содержит общую production-конфигурацию. Чтобы deployment не зависел от названия прежнего провайдера, вводится профиль `production` и файл `production.properties`. Dockerfile собирает WAR через `-Pproduction`.

Переход выполняется без изменения значений и поведения, не связанных с Koyeb. Старый профиль `heroku` можно временно оставить для совместимости с `Procfile`, но он не используется новым Docker-образом. Удаление старой Heroku-конфигурации выполняется отдельной задачей после успешного выпуска.

Production-конфигурация обязана:

- получать внешний адрес из `APP_HOST`;
- получать базу только из `DATABASE_URL`;
- получать ключ remember-me из `REMEMBER_ME_KEY`;
- не требовать SMTP и Facebook OAuth, если они явно отключены;
- отключать mail debug;
- не содержать локальных путей, паролей и действующих credentials.

## 7. Контракт окружения

### 7.1. Обязательные значения

| Переменная | Секрет | Правило |
|---|---:|---|
| `APP_HOST` | нет | Публичный URL Koyeb вида `https://<service>.koyeb.app`, без завершающего `/` |
| `DATABASE_URL` | да | Neon runtime URL с ограниченной ролью и `sslmode=verify-full` |
| `MIGRATION_DATABASE_URL` | да | Прямой Neon URL миграционной роли с DDL-правами и `sslmode=verify-full` |
| `REMEMBER_ME_KEY` | да | Случайное значение не менее 32 байт |
| `PORT` | нет | Передаётся Koyeb; локальное значение по умолчанию — `8080` |

### 7.2. Ограничение ресурсов

Начальная конфигурация для первого измерения:

| Переменная | Начальное значение | Назначение |
|---|---|---|
| `JAVA_TOOL_OPTIONS` | `-Xms64m -Xmx256m -XX:MaxMetaspaceSize=96m -Xss512k -XX:+UseSerialGC` | Ограничить heap, metaspace и накладные расходы GC |
| `DB_POOL_INITIAL_SIZE` | `0` | Не удерживать лишнее соединение при старте пула |
| `DB_POOL_MAX_SIZE` | `3` | Ограничить память и соединения Neon |
| `TOMCAT_MAX_THREADS` | `20` | Ограничить число request threads |
| `TOMCAT_ACCEPT_COUNT` | `20` | Ограничить очередь запросов |

Значения JVM являются стартовой гипотезой. После измерений разрешено перераспределять память между heap и metaspace, но контейнер должен иметь не менее 80 МБ запаса относительно лимита Koyeb на прогретом smoke-тесте. Увеличивать `-Xmx` без повторной проверки native memory нельзя.

`TOMCAT_MAX_THREADS` и `TOMCAT_ACCEPT_COUNT` добавляются в entrypoint как проверяемые положительные целые значения и применяются к HTTP Connector. Некорректное значение останавливает запуск с сообщением без секретов.

### 7.3. Необязательные интеграции

Для первого выпуска допускается:

```text
SMTP_ENABLED=false
FACEBOOK_CLIENT_ID=disabled
FACEBOOK_SECRET=disabled
```

Если в базе есть профили `RESET_REQUIRED`, публикация без рабочего recovery-канала запрещена. В этом случае SMTP настраивается отдельными secrets и проверяется реальная доставка письма. Значение `mail.debug` в production всегда `false`.

## 8. База данных и миграции

### 8.1. Создание Neon

- создать отдельный production-проект, не переиспользуя локальную БД;
- выбрать европейский регион, ближайший к Frankfurt;
- создать отдельную роль приложения с минимально необходимыми правами;
- использовать production branch как единственный источник постоянных данных;
- сохранить connection string только в Koyeb Secret `DATABASE_URL`;
- проверить наличие `sslmode=verify-full` после любых преобразований URL.

Для runtime допускается pooled endpoint Neon после проверки транзакционных сценариев. Flyway всегда использует отдельный прямой endpoint из `MIGRATION_DATABASE_URL`: совместное использование transaction pooler для Flyway 6.5.7 не допускается. Runtime-роль не получает DDL-права, а миграционная роль не используется обычным datasource. Нельзя одновременно открыть больше runtime-соединений, чем задано `DB_POOL_MAX_SIZE`.

### 8.2. Flyway

- пустая база автоматически получает `V1`, затем последующие миграции;
- непустая база без `flyway_schema_history` не принимается автоматически;
- существующую legacy-базу можно подключить только после backup, schema diff и явного baseline согласно ADR-0002;
- Hibernate не создаёт и не обновляет production-схему;
- повторный запуск контейнера не меняет уже применённые миграции;
- ошибка миграции блокирует создание Spring context, поэтому liveness и readiness не становятся доступны.

### 8.3. Backup и восстановление

До первого импорта и перед каждой необратимой миграцией выполняется `pg_dump` в зашифрованное хранилище вне Koyeb. Для backup задаются владелец, дата создания и срок хранения. Не реже одного раза до публичного запуска выполняется тестовое восстановление в отдельную Neon branch или временную PostgreSQL.

Встроенное окно восстановления Neon дополняет, но не заменяет проверенный логический backup.

## 9. Контейнер и сборка

Используется существующая multi-stage схема:

1. Maven-stage собирает WAR из чистого checkout.
2. Runtime-stage содержит закреплённый Tomcat 9 и JRE 8.
3. WAR копируется как `/usr/local/tomcat/webapps/ROOT.war`.
4. Контейнер запускается от `tomcat-app`.

Дополнительные требования для Koyeb:

- Docker build context — корень репозитория;
- Dockerfile — `docker/tomcat/Dockerfile`;
- image не содержит `.env`, `.runtime`, `.tools`, `target` и Git metadata;
- entrypoint не записывает секреты и принимает platform `PORT`;
- локальные файлы считаются расходными и не используются как источник истины;
- сборка не зависит от заранее созданного WAR;
- Dockerfile закрепляет patch-версии build/runtime-образов; полная побайтовая воспроизводимость без pin по digest не обещается, а обновление digest выполняется отдельным проверенным изменением.

## 10. Настройка Koyeb

Web Service создаётся со следующими параметрами:

| Параметр | Значение |
|---|---|
| Source | GitHub-репозиторий GoodCourses |
| Builder | Dockerfile |
| Dockerfile path | `docker/tomcat/Dockerfile` |
| Region | Frankfurt |
| Instance | `free` |
| Instances | 1 |
| Public route | `/` |
| Port | значение `PORT`, ожидаемое контейнером |
| Health protocol | HTTP |
| Health path | `/health/live` |
| Health grace period | не меньше измеренного холодного старта плюс 30 секунд |

Автоматический deployment из `master` включается только после успешного первого ручного выпуска. До этого Koyeb привязывается к deployment-ветке. Pull request и непроверенные ветки не должны автоматически заменять production.

После создания сервиса владелец проверяет Usage and billing: Starter, один Web Service, instance `free`, отсутствие Database Service, Volume и других платных ресурсов.

## 11. Health-check и холодный старт

`GET /health/live` подтверждает работу web-процесса и не обращается к Neon. `GET /health/ready` выполняет ограниченную по времени проверку БД и возвращает `503`, пока приложение, миграции или БД не готовы.

Koyeb использует liveness как единственный platform probe. Это предотвращает restart loop при краткой недоступности Neon; до завершения Spring context endpoint всё равно недоступен. Readiness проверяется отдельным smoke-тестом после каждого выпуска и мониторингом, но не служит сигналом перезапуска. Platform timeout задаётся не меньше 5 секунд, interval — 30 секунд, initial grace period — не меньше измеренного холодного старта плюс 30 секунд. Ответы health endpoints не содержат версию БД, host, credentials, stack trace и другие инфраструктурные подробности.

Целевой холодный старт от scale-to-zero до успешного readiness — не более 180 секунд. Если лимит стабильно превышается, сначала анализируются CPU, Flyway, создание Spring context и подключение Neon. Искусственный keep-alive, обходящий scale-to-zero бесплатного тарифа, не используется.

## 12. Безопасность

- все публичные запросы принимаются только по HTTPS;
- session и remember-me cookies используют `Secure`, `HttpOnly` и согласованный `SameSite`;
- `APP_HOST`, а не входящий Host header, используется для внешних callback URL;
- forwarded-заголовки не считаются доверенными приложением; отдельный `RemoteIpValve` без документированных proxy ranges Koyeb не включается;
- Tomcat CookieProcessor задаёт `SameSite=Lax` для session и remember-me cookies;
- CSRF остаётся включённым для изменяющих запросов;
- секреты создаются в Koyeb как Secret, а не обычный текстовый build argument;
- `DATABASE_URL`, пароли, токены, cookie и SMTP credentials не выводятся в логи;
- Docker image и dependency tree проверяются на непринятые Critical/High уязвимости;
- административные endpoint и отладочные режимы не публикуются;
- размеры upload и form requests ограничиваются существующей серверной валидацией либо отдельной настройкой до включения загрузок.

## 13. Наблюдаемость и диагностика

Приложение пишет структурированно различимые сообщения в stdout/stderr для следующих событий:

- начало и успешное завершение запуска;
- номер применяемой Flyway-миграции без данных пользователей;
- отказ конфигурации с названием переменной, но без её значения;
- потеря соединения с БД без полного URL;
- корректное завершение процесса.

Для диагностики OOM используются метрики Koyeb и причина завершения контейнера. Heap dump не сохраняется на локальный диск как единственный артефакт: свободного места и постоянства диска недостаточно. При необходимости проблема воспроизводится локально с лимитом 512 МБ.

## 14. Процесс выпуска

1. Проверить актуальные условия Koyeb Free и Neon Free.
2. Собрать image локально с ограничением памяти 512 МБ.
3. Выполнить применимые тесты и smoke-тест.
4. Создать Neon production project и отдельные credentials.
5. Проверить миграции на пустой базе или на восстановленной копии.
6. Создать Koyeb Web Service из deployment-ветки.
7. Задать secrets и resource variables.
8. Убедиться, что выбран instance `free` и не созданы платные ресурсы.
9. Выполнить deployment и дождаться readiness.
10. Провести позитивные и негативные пользовательские сценарии.
11. Перезапустить сервис и выполнить повторный deployment.
12. Подтвердить сохранность записей в Neon.
13. После наблюдения включить deployment из `master`.

## 15. Откат

При проблеме приложения Koyeb переключается на последний проверенный image или commit. Откат разрешён, только если предыдущая версия совместима с уже применённой схемой и не возвращает небезопасное хранение паролей.

Перед несовместимой миграцией Koyeb Web Service ставится на паузу: новые запросы прекращаются, активные операции завершаются, затем создаётся backup. Миграции по умолчанию выполняются по expand/contract и остаются обратно совместимыми хотя бы с предыдущим image, поэтому пауза требуется только для явно несовместимого изменения. Целевые показатели для hobby-стенда: RPO 0 для планового выпуска и RTO до 60 минут. В аварии вне планового выпуска RPO ограничивается последним проверенным backup и окном восстановления Neon.

Если проблема вызвана миграцией:

- Koyeb Web Service остаётся на паузе до восстановления и успешной ручной проверки readiness;
- destructive rollback SQL вручную не выполняется без отдельного плана;
- выпускается корректирующая forward migration либо восстанавливается проверенный backup в новую базу/branch;
- после остановки записей и проверки целостности `DATABASE_URL` переключается на восстановленную БД одним изменением secret и новым deployment;
- старую базу не удаляют до подтверждения целостности.

## 16. Стратегия проверки

### 16.1. Автоматические проверки

- `mvn package -DskipTests` собирает WAR;
- применимые модульные и интеграционные тесты проходят;
- Docker image собирается из чистого checkout;
- production стартует без необязательных SMTP/OAuth;
- отсутствие обязательного secret приводит к fail-fast;
- `DATABASE_URL` без `sslmode=verify-full` отклоняется;
- некорректные `PORT`, `TOMCAT_MAX_THREADS` и `TOMCAT_ACCEPT_COUNT` отклоняются;
- Flyway проходит на пустой БД и повторный запуск идемпотентен;
- liveness не зависит от БД, readiness возвращает `503` при её недоступности;
- repository и image не содержат secrets и локальные каталоги.

### 16.2. Ручные сценарии

- открыть каталог как гость;
- зарегистрироваться, войти и выйти;
- проверить восстановление пароля, если SMTP включён;
- изменить собственный профиль и навыки;
- добавить курс в профиль;
- создать, изменить и удалить собственный отзыв;
- убедиться, что другой пользователь не может менять чужие данные;
- проверить CSRF-отказ без токена;
- создать контрольную запись, перезапустить Koyeb и проверить её наличие;
- выполнить новый deployment и повторно проверить запись;
- дождаться scale-to-zero, измерить холодный старт и проверить пользовательский сценарий.

### 16.3. Проверка ресурсов

Тест выполняется локально и затем в Koyeb:

- прогреть каталог, авторизацию, профиль, курсы и отзывы;
- выполнить не менее 30 минут смешанной нагрузки до пяти одновременных пользователей;
- подтвердить отсутствие OOM, непрерывных рестартов и исчерпания DB pool;
- обеспечить не менее 80 МБ запаса памяти после прогрева;
- зафиксировать холодный старт и время основных запросов;
- подтвердить p95 каталога не более 3 секунд, p95 обычной записи не более 5 секунд и p95 BCrypt-входа не более 5 секунд при одном активном пользователе;
- при смешанной нагрузке до пяти пользователей подтвердить p95 основных запросов не более 10 секунд без устойчивого CPU throttling;
- проверить восстановление после кратковременной недоступности Neon.

Если приложение не укладывается в лимит, сначала уменьшаются лишние потоки и кэши, анализируется metaspace и исключаются ненужные runtime-компоненты. Переход на Spring Boot не считается автоматическим способом снижения памяти и рассматривается отдельным архитектурным решением.

## 17. Критерии приёмки

1. Koyeb показывает Starter, один Web Service и instance `free`; платные ресурсы отсутствуют.
2. Приложение доступно по HTTPS и использует внешний URL из `APP_HOST`.
3. Контейнер стабильно запускается в 512 МБ и не перезапускается из-за OOM.
4. Холодный старт укладывается в 180 секунд.
5. `/health/live` и `/health/ready` выполняют разные функции, Koyeb использует liveness, а readiness проверяется smoke-тестом.
6. Neon подключён с `sslmode=verify-full` и пулом не более трёх соединений.
7. Flyway создаёт пустую схему и не изменяет её при повторном старте.
8. Данные сохраняются после restart, redeploy и scale-to-zero Koyeb.
9. Секреты отсутствуют в Git, image, build args и runtime-логах.
10. Проверены регистрация, вход, профиль, навыки, курсы и отзывы, включая запрет изменения чужих данных.
11. Создан и тестово восстановлен логический backup.
12. Документированы фактические значения памяти, холодного старта, URL стенда, версия image и процедура отката.

## 18. Риски и условия остановки выпуска

Публикация блокируется, если:

- контейнер не помещается в 512 МБ либо циклически перезапускается;
- readiness не становится успешным за 180 секунд;
- приложение теряет данные после restart/redeploy;
- Flyway не может однозначно определить состояние схемы;
- в БД остаются открытые пароли или нет recovery-канала для `RESET_REQUIRED`;
- TLS Neon не проверяет сертификат и имя хоста;
- в логах или image обнаружены secrets;
- панель Koyeb показывает платный ресурс или отличный от `free` instance;
- обнаружена непринятая Critical/High уязвимость, применимая к публичному стенду.

При срабатывании ресурсных условий сначала фиксируются измерения. Затем принимается отдельное решение: оптимизировать текущий runtime, перейти на недорогой instance Koyeb/Heroku либо использовать Cloud Run с финансовыми ограничениями.

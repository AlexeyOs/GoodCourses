# Production-развёртывание GoodCourses

Документ описывает первый публичный стенд по [issue #65](https://github.com/AlexeyOs/GoodCourses/issues/65). Архитектурные ограничения и критерии безопасности находятся в [SDD](specifications/issue-65-production-deployment.md).

## 1. Предварительные условия

- Docker с поддержкой multi-stage build;
- Neon PostgreSQL;
- Docker-хостинг с HTTPS, secrets и HTTP health-check;
- публичный URL приложения;
- SMTP, если существуют профили в состоянии `RESET_REQUIRED`.

## 2. Переменные окружения

Шаблон находится в `.env.example`. Реальные значения нельзя сохранять в Git, Docker image или логи.

Обязательные переменные:

| Переменная | Назначение |
|---|---|
| `APP_HOST` | внешний HTTPS URL приложения |
| `DATABASE_URL` | Neon URL с `sslmode=verify-full` |
| `REMEMBER_ME_KEY` | длинное случайное значение |

Для SMTP задаются `SMTP_ENABLED=true`, хост, порт, пользователь, пароль и адрес отправителя. Facebook OAuth можно оставить отключённым значениями `disabled`.

## 3. База данных

Flyway запускается при старте приложения.

- Пустая БД получает `V1`, затем последующие миграции.
- Непустая БД без `flyway_schema_history` по умолчанию останавливает запуск. Перед первым production-запуском оператор обязан сверить её со схемой V1, проверить ограничения отзывов и рейтингов и только для первого запуска установить `FLYWAY_BASELINE_ON_MIGRATE=true`. После появления истории значение возвращается в `false`.
- Миграция credentials удаляет открытые пароли и переводит такие профили в `RESET_REQUIRED`. Перед её применением обязателен зашифрованный backup с ограниченным сроком хранения.

Проверка отсутствия открытых credentials после миграции:

```sql
SELECT COUNT(*) AS plaintext_credential_count
FROM profile
WHERE password IS NOT NULL
  AND (password_state <> 'ACTIVE'
       OR password !~ '^\$2[aby]\$[0-9]{2}\$[./A-Za-z0-9]{53}$');
```

Результат перед публикацией должен быть `0`.

## 4. Сборка образа

```bash
docker build -f docker/tomcat/Dockerfile -t goodcourses:issue-65 .
```

Образ собирает WAR внутри Maven-stage и запускает его в закреплённой версии Tomcat от непривилегированного пользователя.

## 5. Проверка состояния

- `GET /health/live` проверяет процесс без обращения к БД.
- `GET /health/ready` выполняет ограниченный по времени `SELECT 1`.

Хостинг должен использовать `/health/ready`. Endpoint возвращает `503`, если Neon недоступен, и не раскрывает детали соединения.

## 6. Порядок выпуска

1. Собрать образ и выполнить тесты.
2. Проверить миграции на копии БД.
3. Создать зашифрованный backup и проверить восстановление.
4. Настроить secrets в панели хостинга.
5. Развернуть новый image и дождаться readiness.
6. Убедиться, что `plaintext_credential_count = 0`.
7. Проверить регистрацию, вход, logout, восстановление пароля, профиль, курсы и отзывы.
8. Проверить отрицательные сценарии CSRF и доступ к чужим данным.

## 7. Откат

Откат разрешён только на image с BCrypt и совместимой схемой. Нельзя возвращать версию с `NoOpPasswordEncoder`. Если миграция несовместима со старым image, восстанавливается проверенный post-migration backup либо выпускается новая корректирующая миграция.

Старый backup с открытыми credentials удаляется после подтверждения нового backup и завершения согласованного срока хранения.

## 8. Ограничения бесплатного стенда

Хостинг может останавливать контейнер при простое, поэтому первый запрос бывает медленным. Лимиты compute, соединений Neon и условия тарифов нужно проверять перед каждым существенным увеличением нагрузки.

# Production-развёртывание GoodCourses

Документ описывает первый публичный стенд по [issue #65](https://github.com/AlexeyOs/GoodCourses/issues/65). Архитектурные ограничения и критерии безопасности находятся в [SDD](specifications/issue-65-production-deployment.md).

## 1. Предварительные условия

- Docker с поддержкой multi-stage build;
- Neon PostgreSQL;
- Docker-хостинг с HTTPS, secrets и HTTP health-check;
- публичный URL приложения;
- SMTP, если существуют профили в состоянии `RESET_REQUIRED`.

## 2. Переменные окружения

Шаблон находится в `.env.example`. Реальные значения нельзя сохранять в Git, Docker image или логи.

Обязательные переменные:

| Переменная | Назначение |
|---|---|
| `APP_HOST` | внешний HTTPS URL приложения |
| `DATABASE_URL` | Neon URL ограниченной runtime-роли с `sslmode=verify-full` |
| `MIGRATION_DATABASE_URL` | прямой Neon URL отдельной роли Flyway с `sslmode=verify-full` |
| `REMEMBER_ME_KEY` | длинное случайное значение |

Для SMTP задаются `SMTP_ENABLED=true`, хост, порт, пользователь, пароль и адрес отправителя. Facebook OAuth можно оставить отключённым значениями `disabled`.

## 3. База данных

Flyway запускается при старте приложения.

Для публичного стенда используются две строки подключения:

- `DATABASE_URL` — runtime-роль с `CONNECT`, `USAGE` схемы и DML/sequence-правами без `CREATE`, `ALTER` и `DROP`;
- `MIGRATION_DATABASE_URL` — прямой Neon endpoint миграционной роли, владеющей объектами и выполняющей Flyway DDL.

Права runtime-роли выдаются миграционной ролью через `ALTER DEFAULT PRIVILEGES` для будущих таблиц и sequence. После первого запуска у runtime-роли явно отзываются права на `flyway_schema_history`. Названия ролей и пароли не сохраняются в SQL-файлах репозитория. Проверка прав выполняется отдельными подключениями: runtime-роль должна читать и изменять бизнес-таблицы, но получать отказ на `CREATE TABLE` и изменение Flyway history.

- Пустая БД получает `V1`, затем последующие миграции.
- Непустая БД без `flyway_schema_history` всегда останавливает запуск: приложение не умеет автоматически объявлять произвольную legacy-схему версией V1. Для такой БД сначала создаётся backup, выполняется полный schema diff с V1 и отдельная явная команда Flyway `baseline` версии 1. Только после успешной проверки приложение может применять V2 и V3.
- Миграция credentials удаляет открытые пароли и переводит такие профили в `RESET_REQUIRED`. Перед её применением обязателен зашифрованный backup с ограниченным сроком хранения.

Проверка отсутствия открытых credentials после миграции:

```sql
SELECT COUNT(*) AS plaintext_credential_count
FROM profile
WHERE password IS NOT NULL
  AND (password_state <> 'ACTIVE'
       OR password !~ '^\$2[aby]\$[0-9]{2}\$[./A-Za-z0-9]{53}$');
```

Результат перед публикацией должен быть `0`.

## 4. Сборка образа

```bash
docker build -f docker/tomcat/Dockerfile -t goodcourses:issue-65 .
```

Образ собирает WAR внутри Maven-stage и запускает его в закреплённой версии Tomcat от непривилегированного пользователя.

Локальная проверка лимита бесплатного Koyeb:

```bash
docker run --rm --memory=512m --cpus=0.1 \
  --env-file .env \
  -p 8080:8080 \
  goodcourses:issue-65
```

## 5. Проверка состояния

- `GET /health/live` проверяет процесс без обращения к БД.
- `GET /health/ready` выполняет ограниченную по времени проверку БД.

Koyeb использует `/health/live` как platform health-check, чтобы краткий сбой Neon не перезапускал здоровый процесс. `/health/ready` проверяется smoke-тестом после выпуска и возвращает `503`, если Neon недоступен, не раскрывая детали соединения.

## 6. Порядок выпуска

1. Собрать образ и выполнить тесты.
2. Проверить миграции на копии БД.
3. Создать зашифрованный backup и проверить восстановление.
4. Настроить secrets в панели хостинга.
5. Развернуть новый image, дождаться liveness и отдельно проверить readiness.
6. Убедиться, что `plaintext_credential_count = 0`.
7. Проверить регистрацию, вход, logout, восстановление пароля, профиль, курсы и отзывы.
8. Проверить отрицательные сценарии CSRF и доступ к чужим данным.

## 7. Настройка Koyeb

1. Создать Web Service из GitHub-репозитория.
2. Выбрать сборку через `docker/tomcat/Dockerfile` с context из корня репозитория.
3. Выбрать регион Frankfurt, один instance типа `free` и публичный route `/`.
4. Добавить значения из `.env.example`; реальные `DATABASE_URL`, `MIGRATION_DATABASE_URL` и `REMEMBER_ME_KEY` создать как Secrets.
5. Настроить HTTP health-check `/health/live`, timeout 5 секунд, interval 30 секунд и initial grace period не меньше фактически измеренного холодного старта плюс 30 секунд.
6. После запуска вручную проверить `/health/ready` и основные пользовательские сценарии.
7. Проверить Usage and billing: Starter, один бесплатный Web Service, без Koyeb Database, Volume, Worker и платных экземпляров.

Первый выпуск выполняется из ветки развёртывания. Автоматическое обновление из `master` включается только после успешного restart/redeploy теста и проверки сохранности контрольной записи в Neon.

## 8. Откат

Откат разрешён только на image с BCrypt и совместимой схемой. Нельзя возвращать версию с `NoOpPasswordEncoder`. Если миграция несовместима со старым image, восстанавливается проверенный post-migration backup либо выпускается новая корректирующая миграция.

Старый backup с открытыми credentials удаляется после подтверждения нового backup и завершения согласованного срока хранения.

Перед несовместимой миграцией Koyeb Web Service ставится на паузу, после завершения активных операций создаётся backup. Предпочтительны обратно совместимые expand/contract-миграции. Для планового выпуска цель — RPO 0 и восстановление не дольше 60 минут.

## 9. Ограничения бесплатного стенда

Хостинг может останавливать контейнер при простое, поэтому первый запрос бывает медленным. Лимиты compute, соединений Neon и условия тарифов нужно проверять перед каждым существенным увеличением нагрузки.

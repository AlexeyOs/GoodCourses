# Инструкции для AI-агентов проекта GoodCourses

## Назначение проекта

GoodCourses — веб-приложение для размещения информации об обучающих IT-курсах и пользовательских отзывов.

## Технологии

- Java 8
- Spring MVC 5
- Spring Security
- Spring Data JPA
- Hibernate
- JSP и JSTL
- PostgreSQL
- Maven
- Tomcat 9
- JUnit 4

## Общие правила

- Перед изменениями изучить связанные контроллеры, сервисы, репозитории, сущности и JSP.
- Следовать существующей архитектуре проекта.
- Не выполнять несвязанный рефакторинг.
- Не изменять публичное поведение вне поставленной задачи.
- Не добавлять новые зависимости без необходимости.
- Не коммитить секреты, пароли, токены и локальные пути.
- Не коммитить `.runtime/`, `.tools/`, `target/` и локальные файлы окружения.
- Пользовательские данные из HTTP-запросов всегда считать недоверенными.
- После изменений проверять сборку и основной пользовательский сценарий.

## Распределение ответственности

### Основной агент

Отвечает за задачу целиком.

Обязанности:

- анализировать требования;
- определять границы задачи;
- составлять план реализации;
- распределять независимые части работы между специализированными агентами;
- проверять совместимость изменений;
- разрешать конфликты архитектурных решений;
- выполнять итоговую сборку;
- проводить сквозную проверку;
- готовить ветку, коммит и pull request.

Основной агент остаётся ответственным за конечный результат, даже если часть работы выполнялась другими агентами.

### Backend-агент

Отвечает за серверную логику.

Область работы:

- JPA-сущности;
- Spring Data-репозитории;
- сервисы;
- контроллеры;
- транзакции;
- валидация;
- авторизация;
- SQL-схема.

Правила:

- контроллеры должны заниматься привязкой HTTP-параметров, вызовом сервисов и выбором ответа;
- бизнес-правила должны находиться в сервисном слое;
- репозитории должны отвечать только за получение и сохранение данных;
- операции изменения и удаления должны проверять владельца сущности;
- нельзя доверять идентификаторам, полученным из формы;
- проверку прав нельзя оставлять только на уровне интерфейса;
- бизнес-ограничения необходимо по возможности закреплять ограничениями PostgreSQL;
- изменения SQL должны соответствовать JPA-моделям;
- связанные изменения должны выполняться в одной транзакции.

### Frontend-агент

Отвечает за JSP-интерфейс и клиентское поведение.

Область работы:

- JSP;
- tag-файлы;
- JSTL;
- HTML;
- CSS;
- JavaScript;
- меню и навигация;
- формы и сообщения об ошибках.

Правила:

- элементы управления должны быть заметными и понятными;
- действия владельца не должны отображаться другим пользователям;
- сокрытие кнопки не считается проверкой безопасности;
- формы должны показывать ошибки валидации;
- для пустых списков нужно показывать объяснение и доступное следующее действие;
- ссылки должны учитывать `pageContext.request.contextPath`;
- JavaScript не должен содержать бизнес-логику;
- интерфейс должен оставаться работоспособным без JavaScript, если это практически возможно;
- пользовательский текст должен выводиться безопасно;
- изменения должны соответствовать используемой версии Bootstrap.

### QA-агент

Отвечает за проверку функциональности и поиск регрессий.

Область работы:

- модульные тесты;
- интеграционные тесты;
- MockMvc;
- проверка SQL;
- ручные HTTP-сценарии;
- проверка интерфейса;
- анализ логов.

Для функций, связанных с пользовательскими данными, необходимо проверить:

- авторизованного владельца;
- другого авторизованного пользователя;
- неавторизованного пользователя;
- корректные данные;
- пустые и некорректные данные;
- несуществующий идентификатор;
- повторную отправку формы;
- попытку изменить или удалить чужую запись;
- пустое состояние списка.

QA-агент не исправляет найденные проблемы без согласования с основным агентом. Он описывает:

- шаги воспроизведения;
- ожидаемый результат;
- фактический результат;
- уровень критичности;
- затронутые файлы или компоненты.

## Архитектурные требования

### Контроллеры

- Не размещать в контроллерах сложную бизнес-логику.
- Не обращаться к нескольким репозиториям напрямую, если операция относится к одному бизнес-сценарию.
- Использовать сервисный слой.
- После успешного POST использовать redirect.
- Защищённые маршруты явно добавлять в Spring Security.

### Сервисы

- Проверять существование сущностей.
- Проверять принадлежность данных текущему пользователю.
- Использовать `@Transactional` для операций изменения.
- Возвращать понятные доменные ошибки.
- Не принимать объект `Profile` из пользовательской формы как подтверждение владельца.

### Репозитории

- Для пользовательских данных предпочитать запросы вида `findByIdAndProfileId(...)`.
- Методы, которые могут вернуть несколько записей, должны возвращать `List` или `Page`.
- Для списков потенциально неограниченного размера использовать пагинацию.

### JSP и формы

- Не передавать через форму данные, которые можно безопасно получить из текущей сессии.
- Не использовать переданный `profileId` как подтверждение личности пользователя.
- Использовать серверную валидацию независимо от HTML-атрибутов.
- После ошибки сохранять введённые пользователем значения.
- Для опасных действий показывать понятное подтверждение.

### База данных

- JPA-аннотации и SQL-схема должны соответствовать друг другу.
- Уникальность бизнес-сущностей должна обеспечиваться ограничениями базы.
- Внешние ключи должны предотвращать появление осиротевших записей.
- Удаление данных должно быть осознанным и проверенным.
- Изменение существующей схемы должно сопровождаться обновлением SQL-файлов проекта.

## Требования к безопасности

- Все операции создания, изменения и удаления проверяются на сервере.
- Пользователь может изменять только собственные данные.
- Идентификаторы из URL и форм нельзя считать доверенными.
- Нельзя выводить пользовательский HTML без экранирования.
- Нельзя записывать пароли, токены и секреты в логи.
- Нельзя ослаблять Spring Security для упрощения тестирования.
- CSRF нельзя отключать или расширять область его отключения без отдельного решения.

## Проверка изменений

Перед завершением задачи агент должен:

1. Проверить `git diff`.
2. Убедиться, что в изменениях нет секретов и локальных файлов.
3. Выполнить сборку:

   ```powershell
   mvn package -DskipTests
   ```

4. Запустить применимые тесты.
5. Если полная тестовая конфигурация сломана независимо от изменений:
   - выполнить доступные проверки;
   - зафиксировать точную причину;
   - не утверждать, что все тесты прошли.
6. Для веб-функции проверить приложение через Tomcat.
7. Просмотреть серверные логи на наличие ошибок.
8. Проверить позитивный и негативный сценарии.

## Работа с Git

- Использовать отдельную ветку для каждой задачи.
- Рекомендуемый формат ветки: `codex/<краткое-название-задачи>`.
- Не включать в коммит несвязанные изменения.
- Не перезаписывать пользовательские изменения.
- Не выполнять `git reset --hard`.
- Сообщение коммита должно кратко описывать результат.
- В pull request указывать:
  - что реализовано;
  - какие архитектурные решения приняты;
  - как выполнена проверка;
  - известные ограничения;
  - использование AI, если это требуется владельцем проекта.

## Правила совместной работы агентов

- Агенты не должны одновременно редактировать один файл.
- Backend- и Frontend-агенты заранее согласуют модель данных формы.
- QA-агент начинает итоговую проверку после интеграции изменений.
- Специализированные агенты не создают отдельные коммиты без указания основного агента.
- Все спорные архитектурные решения передаются основному агенту.
- Основной агент проверяет изменения каждого специализированного агента перед включением в результат.

## Особенности задачи «Мои отзывы»

Для issue #54 необходимо соблюдать следующие правила:

- пользователь видит только собственные отзывы;
- список доступен только после авторизации;
- изменение и удаление выполняются только с проверкой владельца;
- один пользователь может оставить не более одного отзыва на курс;
- отзыв нельзя сохранить с пустым текстом;
- дата изменения обновляется при редактировании;
- после удаления отзыв исчезает из списка пользователя и со страницы курса;
- из списка отзывов должна быть доступна ссылка на соответствующий курс;
- пустой список должен содержать ссылку на каталог курсов.
